## 四、第 28 题裁决 ★

### 4.1 先确认扫描件那一格

600 dpi 重渲染 p017 第 3 题判断行并放大：

```
28)      29)      30)      31)      32)      33)(4分)
 ×        √        ×        B        D        D
```

**第 28 格是 `×`，不是 `√`。** 它是一笔细斜十字，与紧邻 29 格那个圆头带钩的 `√` 在笔形上完全不同，不存在识读歧义。转写员「扫描件给 ×」的描述属实。

### 4.2 再判程序实际行为

**结论：官方答案 × 正确；第 28 题应记 `F`（meta.json 现有取值正确，无需返工）。转写员 Q1 的推演有误。**

转写员的推演只覆盖了第一个分句（「先输出一行一个整数」——确实恒真），却默认了第二个分句也恒真。**第二个分句不成立**：`decode` 的输出是任意字节序列，**可以含有换行符**，此时「第二行」会裂成多行。

实际编译运行的反例（`paper.md` 还原的 `read3.cpp`，输入按题目「一个整数 + 一个不含空白字符的字符串」的合法约定）：

```
=== Q28 反例 ===
  输入 1 YQpi            base64("a\\nb") -> 解出含换行的字符串
     原始字节: b'-1\r\na\r\nb\r\n'
     按行拆分: ['-1', 'a', 'b']   -> 共 3 行
  输入 1 Cg==            base64("\\n")
     原始字节: b'-1\r\n\r\n\r\n'
     按行拆分: ['-1', '', '']     -> 共 3 行（第二行为空）
  输入 1 YWJjCmRlZg==    base64("abc\\ndef")
     原始字节: b'-1\r\nabc\r\ndef\r\n'
     按行拆分: ['-1', 'abc', 'def'] -> 共 3 行
  输入 0 YWJj            encode 分支对照
     原始字节: b'-1\r\nWVdKag==\r\n'
     按行拆分: ['-1', 'WVdKag==']  -> 共 2 行
```

`YQpi` 这四个字符不含空白，完全符合题面的「合法输入」假设，却让程序输出了 **3 行**——「再输出一行一个字符串」被直接证伪。**故第 28 题判 ×。**

（旁证：`1 AAAA` 会解出三个 `\0` 字节，第二行在终端上呈空行；`1 Cg==` 则多出一个空行。这些都是同一根因的不同表现。）

### 4.3 可直接用作题解「解释」的文字

> 程序第 62 行 `cout << int(table[0]) << endl;` 是无条件执行的，第一行必定是一个整数（`table[0]` 不在 `base[i]` 的覆盖范围内，保持 `0xff`，按有符号 `char` 转 `int` 得 `-1`），这一点没问题。但第二行未必是「一行」：`opt=1` 时执行 `decode`，而 `decode` 还原出的是任意字节序列，完全可能含换行符，此时第二行会裂成多行。例如输入 `1 YQpi`，`YQpi` 解出的是 `"a\nb"`，程序实际输出三行（`-1`、`a`、`b`）。所以「总是……再输出一行一个字符串」不成立，本题判 ×。
